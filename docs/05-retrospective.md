## 最难问题：单 Agent 中决策与校验的职责划分

我最需要梳理的问题，是该如何组织 Agent loop，以及哪些决定交给模型、哪些条件必须由程序保证。当前任务只有少量工具，围绕同一份需求、资料和脚本版本运行，因此我选择单 Agent：模型根据工具反馈决定检索、改稿、检查或结束，程序负责执行动作、维护状态和核对完成条件。讨论中考虑了单 Agent 与多 Agent 的选择，但没有实际实现多 Agent 对照实验。

其中最容易出错的是修改脚本后的检查有效性。我明确要求第二稿不能沿用第一稿的检查通过；落地时由程序分配版本和内容指纹，只有当前稿的时长与规则检查都通过才允许完成。这样在超时压缩、事实修订或工具失败后，模型可以继续决策，而未检查的新稿不会被误报为完成。设计和实际过程见 [循环协议](08-agent-loop.md)、[超时长运行历史](../examples/data-validation/real-baseline-over-duration-001/over-duration/history.json)。

## 学习收获

- 我理解了 Agent loop 中固定执行步骤与动态业务动作的区别：程序可以固定执行请求、校验、工具调用和反馈，但下一步业务动作仍由模型根据实际观察选择。检索故障后的改查和空检索后的请求补充提供了实际例子。
- 我学会了把事实依据和完成条件落实到可检查的数据上。工具描述与参数 Schema 负责让模型调用工具，来源原文、脚本版本和内容指纹则用于核对结果；仅有引用 ID 或模型自报通过，都不足以完成任务。
- 我学会了区分单元测试、离线 Mock 与真实模型验证。119 项测试用于验证实现契约，真实 Trace 用于观察模型是否根据反馈调整；超时长例最终未完成，就应保留 incomplete，不能用事后离线检查补成成功。

上述收获由 AI 协助归纳；对应工程事实见 [需求与验收映射](01-requirements.md)、[效果验证](03-evaluation.md)，不据此声称已进行额外实验。

## 已观察到的问题与处理

检查报告必须绑定版本与内容，只有稿次不能防止误改正文。运行器负责分配版本和指纹，保存新稿后只读新稿报告；同稿复查失败也会撤销旧通过。历史真实正常路径保存了 v1、v2 及重检；当前超时长路径保存了 v1 至 v4，最终 v4 不沿用 v3 的通过报告。

Python 数据类型与模型可见工具协议不同。项目补充六动作 description/JSON Schema、严格解析、调用 ID 配对和无效响应反馈。真实模型曾同时申请多个动作，程序拒绝本轮执行，模型纠正后继续。

事实检查采用原文和封闭表达，能限制无依据扩写，但曾误拒“它支持为视频添加字幕”这样的合理表达。这是当前业务限制，不能将所有检查拒绝都宣传为发现虚假事实；也不能仅凭引用 ID 存在就允许任意结论。

运行环境也影响验证：用户完成依赖安装并在本机直连后成功运行，客户端现默认直连、可选择系统代理。后续也发生间歇连接失败。CapCut 成功中的网络恢复由程序重试完成；P01 工具失败后的查询调整则由模型选择，二者不能混为模型决策证据。

超时长实测经历 7.6→5.3→2.25 秒，压缩曾丢失唯一事实，被规则工具拒绝；最终 v4 恢复原文后遇连接错误并耗尽 12 步，没有最终检查。离线 v4 虽可行，不能代替原任务的检查或改写原始结果。自定义评估 failed 保留，同时说明它已有修订和明确未完成证据，不能把该分类直接等同于考核整项不达标。

20/10 预算复跑在最初两次请求即连接失败，未进入业务工具。独立诊断随后记录宿主列表成功、聊天超时，具体网络原因仍未知；没有证据归因为模型推理慢。一次简化请求漏带头曾导致错误判断，核对源码后确认生产 JSON 请求头一直正确，已纠正且未修改生产客户端。

## 范围取舍与能力边界

资料扩充选择按 profile 隔离产品/客户端、保留来源，而非直接混合四品牌。原包兼容通过不能证明业务语义正确；Canva 两类字幕及网站表述仍需区分，审阅配置暂缓一条，原始内容不改。未引入数据库或向量检索，先验证资料、规则、来源和范围绑定。

批量场景区分“第一稿直接满足短时长”与“超时后修订”，以及“看到空授权范围直接补充”与“观察实际空检索结果后补充”。当前真实记录已展示两种资料不足场景中的实际空检索；自动评估仍不替代文案质量和理由充分性的人工阅读。

先完成 CLI 核心链路，不引入前端、会话恢复、多 Agent 或生产级 Runtime。LangGraph 只承担图调度，业务完成条件由程序维护。Mock 用来验证分支，真实 Trace 用来证明模型观察后作出选择。

8 个 profile 中已有 2 个真实正常成功，其余 6 个仅有 Mock CLI；成功超时修订和重复运行稳定性尚未证明。官方发布平台规则、开放域事实核验等能力未实现，均如实列为边界，不把它们或前端、数据库、向量检索列为原题必交缺口。

## 如果重新做一次：本人提出的后续设想

本人希望在最小链路跑通后尝试以下方向。它们均为后续探索，当前没有实现，也没有效果或成本对比结论。

1. 优化用户体验：增加表单输入、补充问题提示、稿件与检查结果展示；以后再评估会话恢复，减少手工修改 JSON 的操作。
2. 建立更系统的 Agent 评测集：在现有正常、缺信息、资料不足、工具失败和超时长案例上扩展不同产品与表达，固定输入及预期，重复运行后比较完成率、分支覆盖、事实检查误拒与漏判、耗时和 Token 成本。
3. 将工具封装为可复用的 Skill：整理职责、输入输出 Schema、使用示例和能力边界，便于其他任务复用。这里是未来的能力封装设想，当前仍使用六个函数动作及本地工具。
4. 尝试工具向量召回：工具数量增加后，对工具描述进行语义检索，比较与直接声明全部工具的效果和成本；当前动作只有六个，保留直接声明作为基线。
5. 尝试规则向量与关键词混合召回：用于定位相关规则和解释依据，并比较召回遗漏与误召回。适用的硬规则仍由程序完整加载与执行，不能因检索未命中就跳过。当前检索仍为关键词子串匹配，尚无混合召回结果。

若重新安排时间，我会优先固定最小输入、完成条件和评测案例，尽早打通一次真实调用，再依据失败样例决定扩展方向，避免把有限预算提前分散到多项功能上。该安排由 AI 依据本人提出的后续方向协助整理，属于复盘建议。
