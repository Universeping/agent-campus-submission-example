# 方案与技术取舍

业务理解版本：v0.1.0。Python CLI、单 Agent 和模块结构已确认，用户已选定 DeepSeek V4 Pro；LangGraph 小型状态图为推荐方案，待最终确认与版本锁定。当前只有骨架和设计，schemas、工具协议、配置加载及业务逻辑均未实现。

## 已确认的模块划分

| 模块 | 职责 |
| --- | --- |
| `src/main.py` | CLI、输入校验和结果保存，业务决策交给 Agent。 |
| `src/schemas.py` | 输入、素材、脚本、模型动作、工具结果和任务状态。 |
| `src/model.py` | 模型接入与离线 Mock，接口保持一致并区分运行模式。 |
| `src/agent.py` | 中心循环、工具调度、执行上限与结束条件。 |
| `src/tools.py` | 检索、估时、事实与品牌规则检查。 |
| `src/trace.py` | 运行记录。 |

首版使用本地文本资料，结合官方来源与合成测试配置，输出 JSON 和 Markdown。CLI 支持文件输入或终端粘贴 JSON，一次提交对应一次任务。先验证核心链路，后续通过 HTTP API 与前端表单复用同一 Agent 核心；首版不增加 MCP 服务或跨次会话恢复。

模型返回结构化动作，运行器负责校验和调度；不执行模型生成的任意代码。脚本检查绑定版本，修改后重新检查，最终输出对应同一版本的实际检查结果。

## v0.1.0 业务流程设计

1. 读取需求，校验 JSON 格式与必要信息。格式错误给出可修正原因；缺关键信息时请求补充并结束本次任务。
2. 加载适用的产品资料和平台/品牌规则。加载属于运行准备，不强制包装成模型工具。
3. 模型选择检索词并调用素材检索。结果为空或失败时，由模型决定补查、改写查询、请求资料或明确未完成。
4. 模型依据已获得的事实生成结构化草稿，关联分镜与素材/事实 ID，不添加未获支持的能力或效果数据。
5. 模型调用估时与规则检查工具，观察具体问题、位置和原因；检查顺序可由模型选择。
6. 模型根据反馈修订并重检，或说明无法满足。修订生成新版本，旧版检查不能直接用于新版。
7. 模型请求结束，运行器核对最终版本、来源、检查完整性及是否通过；缺少检查时反馈模型，预算耗尽时明确未完成。
8. 输出结果、风险及任务状态，保存脚本、检查报告与 Trace；未完成也保留已有结果及原因。

固定执行骨架可以负责调度与限制；业务动作的选择须有真实模型参与。设置调用上限，并在达到上限时返回明确的未完成状态。

首版缺信息后不阻塞等待，也不恢复会话；用户修改输入后开启新任务。终端输入仅是另一种 JSON 提交方式，不代表多轮会话。模型/工具调用和格式纠正均纳入预算，具体计数规则与上限待确定。

## 三个本地业务工具

| 工具设计名 | 输入含义 | 返回内容 |
| --- | --- | --- |
| `search_materials` | 产品、查询词及所需事实方向 | 匹配资料、来源/事实 ID、事实文本，或空结果与错误。 |
| `estimate_duration` | 指定版本的脚本与估时配置 | 每镜及总时长、是否超出、超出量与估时口径。 |
| `check_rules` | 指定版本脚本及适用规则 | 产品事实依据、品牌与平台规则问题、位置和依据。 |

写稿与修订由模型完成；文件保存由程序完成，不另设业务工具。产品事实检查不能仅验证 ID 存在；拟通过受控事实表达、规则核对和实际案例抽查界定覆盖范围，任意自然语言的完整语义核验尚未解决。

## 模型与配置

DeepSeek 官方接口设计为 `https://api.deepseek.com` 的 Chat Completions，模型标识为 `deepseek-v4-pro`。`.env.example` 声明 `DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL`、`DEEPSEEK_MODEL`，真实密钥只存本地 `.env` 或进程环境。计划优先使用进程环境；当前没有配置加载代码，也未进行真实 API 调用。

模型负责写稿、修订与动作选择，Mock 使用一致接口并标记模式。工具调用消息的衔接、结构化动作解析、thinking 模式兼容性需在接入时验证，不把 API 格式兼容等同于适配器已验证。Trace 不输出内部推理内容。官方文档见 [来源登记](../data/sources.md)。

## 框架取舍

推荐在 `agent.py` 使用 LangGraph `StateGraph`，组织“输入准备 → 模型节点 ↔ 工具节点 → 结束核验 → 输出”。采用少量节点管理业务状态、版本与终止条件；首版不启用持久化会话或托管服务。LangGraph 能提供编排、状态与后续持久化能力，但业务正确性、调用预算和验收证据仍由项目实现。

原生循环依赖较少；LangChain `create_agent` 提供较高层的工具循环。推荐 LangGraph 是为了明确控制本项目的检查和结束条件，用户尚未最终确认框架。安装时记录实际版本并锁定依赖，当前 `requirements.txt` 仍无第三方依赖。

## 输出与后续界面

计划同时显示终端结果并写入 `outputs/<run_id>/result.json`、`script.md`、`checks.json`、`trace.jsonl`。`outputs/` 不提交，实际验收证据另行归档到 `examples/`。脚本包括标题、分镜、画面描述、旁白或字幕、分镜及总时长、来源、风险和任务状态。

CLI 和未来 HTTP API 只承担输入输出适配，共用同一 Agent 核心。业务状态设计成可序列化数据，为后续会话恢复留出空间，但首版不增加恢复命令。
